# M2.7 — Subagent 系统(task 工具 + AGENT.md + subagent loop)

> **Dispatch spec(2026-05-22)。** MILESTONES §M2.7 + ARCHITECTURE §4.2 的产品落地。
> **依赖 M2.5(skill 系统)** — skill 跟 agent 严格分离但共享文件发现/frontmatter 风格,
> M2.5 完成后 M2.7 可启动。

## 背景

subagent 是 leek 哲学里"投资领域天然适合"的 harness 原语(ARCHITECTURE §4.3):
- **Context window 节约**:主 agent 委派"重活"到 subagent,subagent 自己 context 装,返回 digest
- **并行能力**:多 ticker 扫描 (`task("review", "BABA")` × N 并行)
- **不靠 persona 动物园做专业化**:`corpus-expert` 就是 AGENT.md(prompt + 工具子集),不是 Rust 硬编码

scope ~1200-1800 LOC + cargo test +20-40。

## Scope

### A. `task` 工具

新工具 `crates/gateway/src/agent/tools/task.rs`,加入 `tools::specs()` / `tools::dispatch()`:

签名(对齐 CC):
```
task(agent_name?: string, input: string) → { result: string, subagent_turn_id, duration_ms, cost_usd, ... }
```

- `agent_name`:可选,缺省 = `general-purpose`(内置基线)
- `input`:必填,作为 subagent 的 user prompt
- 返回:subagent 的最终 text response(单个 text block),加 metadata 给主 agent 决策

**调用语义**:
- 主 agent 调 task → 父 agent loop 阻塞等 subagent loop 完成 → subagent 完成后 result 进 tool output
- v0 一次性 batch 返回,**不流式** (per ARCHITECTURE locked decision)
- subagent 的 turn 在 vault 里开一行(`parent_turn_id` 链到父 turn)

### B. AGENT.md 文件格式

**三层发现路径**(同 SKILL.md):
- 内置:`harness/agents/<name>/AGENT.md`
- 用户全局:`~/.leek/agents/<name>/AGENT.md`
- 项目级:`<project>/.leek/agents/<name>/AGENT.md`

同名冲突优先级:项目 > 用户 > 内置。

格式(ARCHITECTURE §4.2.1):
```yaml
---
description: <一句话描述这个 agent 能做什么委派工作>
allowed_tools: [...]      # 可选;不给等于全工具集
model: <override>         # 可选;codex OAuth 单 model 时无视
---

<markdown body — 直接作为 subagent 的 system prompt>
```

### C. Agent 加载链路

新 `crates/gateway/src/agents/` 目录(注意是 `agents/`,与 skill 的 `skills/` 分开 — ARCHITECTURE §4.2 强调"与 skill 严格分离"):

- `loader.rs`:启动时扫描三层目录,加载 AGENT.md
- `agent_def.rs`:`AgentDef` struct(name / description / allowed_tools / system_prompt / source_layer / model)
- `AgentRegistry: Arc<HashMap<String, AgentDef>>`,放 AppState

**与 skill 的边界**(严格):
- 文件:SKILL.md vs AGENT.md(名字不同)
- 目录:harness/skills/ vs harness/agents/(目录不同)
- 注册表:SkillRegistry vs AgentRegistry(独立)
- 调用方式:`use_skill(name)` 把 body 注入当前 loop vs `task(agent_name, input)` spawn 子 loop

不许互相 mix(skill 不能被 task spawn,agent 不能被 use_skill 加载)。

### D. Subagent Loop

新 `crates/gateway/src/agent/subagent.rs`(或在 `agent/mod.rs` 中):

- 主 agent loop 看到 task tool call → 进 `spawn_subagent()`:
  1. 从 `AgentRegistry` 找到 `agent_name` 对应的 `AgentDef`
  2. 构造 subagent system prompt(直接用 AgentDef.system_prompt — 不复用主 agent 五段 system prompt!)
  3. 收紧工具集:available_tools = tools::specs() ∩ AgentDef.allowed_tools(如有 allowed_tools)
  4. 开新 codex chat:input 数组 = [user message of input]
  5. 跑同样的 agent loop 代码(M1 guards + M2.5 hooks + M2.6 cost cap 全复用)
  6. 收集 final assistant text → 返回给父 task tool output

**关键**:subagent loop **整套复用主 loop 代码**,只是 system prompt + tools + input 不同。**不写第二份 loop**。

### E. Per-subagent turn_metrics

`vault::turn_metrics` 表加字段(或复用现有):
- `parent_turn_id: Option<String>` — null 表示主 agent turn,非 null 指向父 turn id
- `depth: u32` — 主 agent = 0,subagent = 1,subagent-of-subagent = 2

每个 subagent turn 在 turn_metrics 表里独立一行,跟主 turn 通过 `parent_turn_id` 链。

### F. Depth 上限 + 嵌套

- subagent 也能调 `task` 工具 spawn 子 subagent
- depth 上限默认 2(主 → 子 → 孙就停)
- 超 depth → task tool error,返 "Maximum subagent depth (2) reached"
- 通过 `turn_metrics.depth` 跟踪

### G. 事件透出

subagent 的活动需要让前端能看到:

- 在 canvas 加一类新 artifact:`subagent_card`,kind="subagent",显示:
  - agent_name + input preview(头部)
  - subagent 内部的 tool calls 折叠 list(可展开看)
  - subagent 内部的 cost / wall_clock / iteration count
  - final result preview
- subagent 内部产生的 `tool_lifecycle` / `note_trace` / `search_lifecycle` 等事件,前端**不平铺到主 canvas**,而是聚合到 `subagent_card` 内的折叠区域

事件 source:
- subagent loop 内部 emit 的事件,在 payload 里加 `parent_turn_id` 字段
- frontend store 用 `parent_turn_id` 路由 events 到对应 subagent_card

### H. 内置 AGENT.md

`harness/agents/general-purpose/AGENT.md`:
```yaml
---
description: 通用 worker subagent。接收任意子任务,完成后返回 text digest。
allowed_tools: [...]  # 全集
---

你是被委派的 worker。任务由父 agent 提供,在 input 字段里。

工作流程:
1. 理解任务,如有 ambiguity 在 final response 里说明你的假设
2. 用工具(corpus_search / corpus_read / web_search / web_fetch / update_plan)收集信息
3. 综合,把结果整理成一份 text digest(几百字到几千字,视任务复杂度)
4. final response = 给父 agent 的 single text block,不需要 markdown 章节,但要有 logical 结构

父 agent 拿到你的 result 后会继续主线工作,你的 context 不会被保留。
```

`harness/agents/corpus-expert/AGENT.md`:
```yaml
---
description: 深谙 corpus 的领域 subagent。corpus 跨多文档综合查询时委派给我。
allowed_tools: [corpus_search, corpus_read]
---

你是 corpus 领域专家。你只有两个工具:corpus_search 和 corpus_read。

你的职责:
1. 父 agent 给你一个 corpus 相关问题(往往是"在 corpus 里关于 X 有哪些权威说法?")
2. 你 corpus_search 找 hits → corpus_read 关键 doc → 反复直到完整
3. 综合多 doc 的内容,组织成一份带 cite 的 text answer(每个 claim 后括号标 corpus path)
4. final response = 给父 agent 的 single text block,带至少 3-5 处 corpus path 引用

你**只用 corpus**,不调 web_search 不调 web_fetch — 那些是父 agent 的工作。
```

### I. 不做(v0)

- **不做流式 result 回传**(ARCHITECTURE locked decision,batch 返回)
- **不做 subagent UI 配置面板**(用户编 AGENT.md 文件)
- **不做 cross-session subagent state**(每个 task 调用独立 loop,无 memory)
- **不做 subagent 共享 fixture / cache**(每个 subagent fresh start)
- **不做 subagent 间 message passing**(只通过 task 入参 + return)
- **不做 hook 在 subagent 也触发**(M2.5 hooks 默认只主 agent 触发;subagent hook 触发是后续 enhancement)
