# M3.2 — reasoning status pill + 强制中止按钮(UX 反馈空洞修复)

> **Dispatch spec(2026-05-25)。** 修 M3 deep-review 实测踩到的体验空洞:
> turn 启动后,前几分钟前端 chat 完全无反馈(agent 在 codex reasoning + builtin
> web_search 阶段,没有 assistant_delta event 流入),user 误以为 stuck。
>
> 同时给 user 一个**手动 abort 当前 turn** 的能力(目前只能 kill 整个 gateway 进程)。

## 背景

实测案例:用户发长电科技深度复盘 prompt → 14 分钟 / 12 iter 完成,**iter 2 一个人就独占 4 分 13 秒**(codex 内部 33 次 builtin web_search,SSE response 整段无 assistant_delta,前端死寂)。

虽然 backend 真在工作,但 user 视角完全无信号。M3.1 的 duplicate URL warning 解决了"无意义重复",**没解决"没东西 emit 时 user 不知道在做什么"** 这个更基础的 UX 问题。

## Scope

### A. Frontend — reasoning status pill

`frontend/web/src/Chat.tsx`(或新 `TurnStatusPill.tsx`)在 chat composer 上方加一个固定区域,**只在 turn 进行中显示**(turn 启动 → `assistant_done` 之间):

#### A.1 显示内容

```
🔄 回合进行中 · iter 3 · 已用 1分23秒 · 当前:正在搜索网页(codex 内置)
[强制停止本回合]
```

字段含义:
- **iter 编号**:来自最近的 `tool_lifecycle` / `search_lifecycle` / `assistant_delta` event 的 payload (它们都带 iteration 字段, M2.7 + M1.9 已落地)
- **elapsed time**:从最初的 `message_created` (user role) 时间戳到现在,client-side `Date.now()` 计算,每秒刷新
- **当前状态文字**:按最近 event 类型决定
  - `tool_lifecycle.start` + `data.tool` 已知 → `正在调用 <display_name>`(如 "正在调用 corpus_search")
  - `search_lifecycle.start` → `正在搜索网页(codex 内置)`
  - `assistant_delta` 进来过 → `正在写回答`
  - **none 以上 + 时间 > 5s** → `agent 正在思考...`(reasoning 阶段)
  - **none 以上 + 时间 > 60s** → `深度思考中(可能在 codex 内部多次搜索,不会有进度反馈)`

#### A.2 颜色 / 紧急度

- 默认:静默灰色
- > 60 秒没新 event 进来:轻微黄色
- > 180 秒没新 event 进来:明显黄色 + "时间较长" 提示文字

不要红色 — 红色暗示出错;长 reasoning 不是错,只是慢。

### B. Frontend — 强制中止按钮

Pill 右侧带按钮 `[强制停止本回合]`。点击 → confirm dialog → POST `/api/v1/sessions/{id}/turns/{turn_id}/abort` → 等 backend 响应 → 隐藏 pill。

按钮在以下情况禁用:
- turn 已结束(其实那时 pill 就该消失)

### C. Backend — `POST .../abort` endpoint

新 `crates/gateway/src/api/sessions.rs` 或 `turns.rs` 加:

```
POST /api/v1/sessions/{id}/turns/{turn_id}/abort
→ 204 No Content
```

实现思路:
- 在 `AppState` 加一个 `turn_abort_signals: Arc<RwLock<HashMap<String, tokio::sync::Notify>>>` (turn_id → Notify)
- Agent loop 启动 turn 时注册 Notify,loop 末尾清理
- 主 loop 的 stream poll 跟 `idle_timeout` 类似,用 `tokio::select!` 同时监听 abort_notify
- abort_notify 触发 → drop stream → 主 loop break,turn 落 `stop_reason="user_aborted"`,emit `assistant_done`
- 复用现有的 stop_reason 落 turn_metrics 路径(类似 idle_timeout / wall_clock 处理)

### D. Frontend — abort 后体验

- pill 立刻消失
- chat 在 assistant message 末尾(如果有累积文字)出一行 `🛑 本回合已被你手动停止`
- 失败的 turn 不影响后续 session;用户可以继续发新 prompt

### E. 不做

- 不试图在 abort 时优雅"告知模型"(L1 不可行,跟 M3.1 同理)
- 不做 abort 后 partial result 处理(已 stream 的文字保留,未到的不补)
- 不做 abort countdown / "再等 30 秒否则自动 abort" 之类
- 不动 backend 现有 `idle_timeout` / `wall_clock` 逻辑(那是另一类 timeout,这里只加 user-triggered abort 通道)
- 不动 M3.1 `codex_duplicate_abort`(那是 system-triggered abort,跟用户 abort 独立)

### F. 单测 + 手测

Backend:
- `api/sessions.rs::tests` 或 `turns.rs::tests`:abort_notify 注册 + 触发 + 清理的单测
- mock SSE stream(类似 idle_timeout 测试用过的 mock 模式)→ abort_notify 触发 → 验证 turn 落 stop_reason="user_aborted"

Frontend(若有 test 设施,参考 settings.test.mjs / activation.test.mjs):
- pill 显示 / 隐藏时机(turn lifecycle event 序列驱动)
- 时间累计 + 颜色阈值切换
- abort POST + confirm 流程

手测(汇报里贴):
- a) 跑短 turn(单 corpus_search),验 pill 出现 → tool 进行中 → assistant_delta → 消失
- b) 跑长 turn(可降 cost cap 或用复杂 prompt 模拟),验 pill 跨过 60s → 180s 颜色变化
- c) 跑长 turn,点 abort 按钮,验 turn 立即停 + chat 显示中止文字 + turn_metrics 落 stop_reason="user_aborted"

## 给 executor 的最后一句

修的是 user **真实踩到的痛点**(发完 prompt 4 分钟以为卡死)。重点:
1. **status pill** 文字要诚实("深度思考中" 比 "处理中" 好,user 才能耐心等)
2. **abort 按钮** 是新的 user agency,把"杀整个 gateway"降级成"杀本回合"
3. 不要试图修不可能修的事(reasoning 阶段 codex 不 emit 中间进度,我们没法做"完成 N%"进度条)

spec 跟现实对不上 → stop 来报告。
