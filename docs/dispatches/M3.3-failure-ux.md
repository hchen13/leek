# M3.3 — fatal_error 文案改人话 + idle_timeout 真生效

> **Dispatch spec(2026-05-25)。** 修 M3.2 之后实测踩到的两个真问题:
>
> 1. 用户跑长电科技深度投研 prompt,**iter 7 codex HTTP 调用挂了 5 分钟** 没收到任何 byte,leek 才报 fatal_error — **idle_timeout(默认 90s)按说该 90 秒就杀,实际没生效**
> 2. chat 只显示抽象文字 "本回合调用失败:POST to the codex Responses endpoint" — **user 完全没法判断是网络/codex 服务端/leek bug,该重试还是该改 prompt**

## 失败案例(实测)


## Scope

### A. backend — fatal_error reason 细化

**当前**:`stop_note("fatal_error")` 返一个 generic string。

**改**:fatal_error 落地之前,把具体 error 上下文(HTTP status / 网络异常类型 / 元数据)捕获,在 final assistant message + assistant_done event 里 surface:

```rust
pub enum FatalReason {
    CodexHttp { status: u16, body_excerpt: String },  // 4xx / 5xx
    CodexStreamSilent { silent_secs: u64 },           // SSE 0 bytes 超时
    CodexConnectionFailed { detail: String },         // DNS / connect / TLS / etc.
    CodexMalformed { detail: String },                // 非预期 SSE 格式 / JSON parse
    Unknown { detail: String },                       // fallback
}
```

`mod.rs` 主循环 fatal 分支:之前是简单 anyhow error → "POST to ..."。改为捕获 reason → 落到:
- `turn_metrics.stop_reason` = "fatal_error"(保持)
- `turn_metrics.first_triggered_guard` = null(保持)
- **新字段** `turn_metrics.fatal_reason_kind: Option<String>`(例如 "codex_http_5xx" / "codex_stream_silent" / "codex_connection_failed")
- **新字段** `turn_metrics.fatal_reason_detail: Option<String>`(human-readable)
- `assistant_done.payload` 加 `fatal_reason: Option<{kind, detail, hint}>`,frontend 用它渲染

每个 kind 对应一个 user-facing hint(中文,actionable):

| kind | hint |
|---|---|
| `codex_http_5xx` | "codex 服务端临时不可用,稍后重试通常能解决" |
| `codex_http_4xx` | "请求被 codex 拒绝(可能 token 失效 / 请求超大),建议检查 Settings 里 token / 缩短 prompt 重试" |
| `codex_stream_silent` | "codex 连接静默 {N} 秒被超时杀,可能网络抖动 / codex 临时过载,重试即可" |
| `codex_connection_failed` | "无法连接 codex 服务(DNS / 网络),检查网络后重试" |
| `codex_malformed` | "codex 返回的格式 leek 没处理过,这是 leek 的 bug,请把这个 turn id 给开发者" |

### B. backend — idle_timeout 真生效(查 + 修)

**症状**:default 90 秒按说该 90 秒就 fire,实测等了 5 分钟。

**Likely root cause**(executor 调研验证):
- codex SSE stream 发 keepalive bytes(e.g. `:keepalive\n\n` SSE comment / heartbeat event)
- 当前 idle 检测在 `tokio::time::timeout(idle_timeout, stream.next())` 模式 — 每收到 _任何_ byte 都重置 idle counter,包括 keepalive
- 用户视角:5 分钟没出新 text/tool/notify event,但底层 byte 流没停 → idle 检测器认为 not idle

**修法**(spec 后,executor 调研后再 finalize):
1. 区分 "substantive event"(text_delta / tool_call / search / done / 等)vs "heartbeat / keepalive"
2. idle counter 只在收到 **substantive** event 时重置;keepalive 不算
3. 阈值仍按 `idle_timeout`(default 90s),但**新语义** = "无新进展超过 N 秒"

实施:
- `crates/gateway/src/agent/loop_core.rs` 主循环 stream poll 加 last_substantive_at 时间戳
- 每 SSE byte 通过 `parse_sse_event` 决定是 substantive 还是 heartbeat
- substantive event → reset timer;heartbeat → 不 reset
- timer 跨阈值 → 同 idle_timeout 路径(drop stream + emit fatal with reason `codex_stream_silent`)

### D. frontend — fatal 渲染人话

`frontend/web/src/Chat.tsx` 看到 `assistant_done.stop_reason == "fatal_error"` 且 payload 有 `fatal_reason`:

替换当前 "本回合调用失败:POST ..." → 渲染:


布局:replace generic 错误条 with structured card,黄色边框(非红 fatal 调,因为多数 case 重试就行)。
