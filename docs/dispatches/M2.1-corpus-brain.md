# M2.1 — Corpus Brain UI(wiki graph + session activation overlay)

> **Dispatch spec(2026-05-22)。** REQUIREMENTS §2.5 + MILESTONES §M2.1 的产品落地。
> 右上角常驻 Corpus Brain 显示全 wiki graph,叠加 agent 实际使用 corpus 时的激活状态。
> **不依赖 M2.6 settings,可与之并行做**。

## 背景

- M2(corpus loader + 工具)已完成 commit `0e4e67d`,128 个 wiki 文件已被 BM25 索引
- REQUIREMENTS §2.5 明确 Corpus Brain 价值是 **"让用户看到 corpus 如何参与 agent 工作"**,
  不是普通文件浏览器
- 三种 activation 层级(historical / session / live)在 REQUIREMENTS 已规定,需求清晰
- 现状:前端右上角是空的(没有 Corpus Brain),`Canvas.tsx` 旁边只有 chat + canvas 两栏

## Scope

### A. Backend — wiki graph 数据源

#### A.1 新 API endpoint

`crates/gateway/src/api/corpus.rs` (或新文件) 加:

```
GET /api/v1/corpus/graph
→ {
    "nodes": [
      { "id": "wikis/principles/concepts/circle-of-competence",
        "title": "Circle of Competence",
        "tier": "principles",
        "type": "concept",
        "tags": ["buffett", "munger", "concept", "..."],
        "confidence": "high",
        "directory_path": "wikis/principles/concepts"
      },
      ...
    ],
    "edges": [
      { "source": "<wiki_id_a>", "target": "<wiki_id_b>",
        "weight": 3,           // 共享 tag 数量
        "shared_tags": ["buffett", "concept", "value-investing"]
      },
      ...
    ]
  }
```

#### A.2 Graph 构建逻辑

新加 `crates/gateway/src/corpus/graph.rs`:

- **Nodes**: 遍历 corpus loader 现成的 `Corpus.docs`,**只取 wikis/ 下的**(`tier` 来自 frontmatter
  `tier` 字段,或从 path `wikis/<tier>/...` 推断)
- **Edges**: 双层 — primary 用 **共享 tag**,边权重 = 共享 tag 数;只生成权重 ≥ 2 的边(避免 graph
  过密)
- 单测覆盖:graph 构建在 fixture 上数节点 + 验证边权重计算

graph 在 startup 时构建一次,缓存到 `AppState.corpus_graph: Arc<CorpusGraph>`(corpus 当前不热加载,
graph 也不需热加载;v0 stale-OK)。

### B. Backend — activation 事件透出

**好消息**:现有 `tool_lifecycle` 事件已经携带工具名 + 参数,前端能从中识别 `corpus_search` /
`corpus_read` 调用的 doc id。**不需要新事件**。

但要确保 events 中含足够的 wiki id 信息让前端 map 到 graph node:

- `corpus_read.display_payload.id` 已经是 wiki 路径(e.g. `wikis/principles/concepts/circle-of-competence`)
  → 前端 directly map
- `corpus_search.display_payload.hits[].id` 类似 → 前端 map 每个 hit 都激活

**Executor 自查**:在 events.json 里 grep 一个真实 corpus_search / corpus_read 事件,确认 id 形态
跟 graph node id 对得上;不对则在 backend 统一 id 格式。

### C. Frontend — CorpusBrain.tsx 组件

#### C.1 Layout

三栏布局现在是 `Sessions │ Chat │ Canvas`。M2.1 改成 **`Sessions │ Chat │ Canvas │ CorpusBrain`**
四栏?太挤。

**推荐方案**:Canvas + CorpusBrain **共享右栏**,用 tab 切换(默认 Canvas,tab 切到 CorpusBrain)。
Tab 上方加 badge 显示"当前 turn 触发的 wiki 节点数",让用户知道有新激活。

或者:CorpusBrain **悬浮在右上角**(像 PlanWidget 那样浮窗),不占主布局空间。

**Executor 选**:
- 简单 PoC:tab 切换最少 layout 改动
- 浮窗:UX 更轻量但浮窗管理复杂

推 **tab 切换** + 未来若 UX 不好再改浮窗。

#### C.2 Graph 渲染

**渲染方案选项**(executor 调研后选):

**X. 手写 SVG + 简单 force-directed layout**
- Pros:无依赖,完全可控,128 nodes 性能 OK
- Cons:layout 算法要自己写(D3 风格 force simulation,~80 行 TS)

**Y. sigma.js**(vanilla JS,需要在 Solid mount 中包装)
- Pros:成熟,WebGL 后端,支持大 graph
- Cons:增加依赖(~50KB),Solid 集成稍 ugly

**Z. d3-force + 手写 svg**(用 d3 算 layout,自己渲 svg)
- Pros:layout 久经考验
- Cons:d3 是大库(~80KB),整套引入太重

**推 X**(手写,scope ~250 行),除非 worker 调研发现性能问题。

#### C.3 节点视觉

- 颜色编码:
  - **tier=principles**: 蓝色
  - **tier=knowledge**: 绿色
- 大小编码:
  - **confidence=high**: 大
  - **confidence=medium/low**: 中/小
- 文字标签:**hover 才显示**(节点 size 太小直接显示挤);click 节点 → modal 显示 frontmatter
  + 第一段 body preview + "查看完整内容"按钮跳 corpus_read

#### C.4 Activation overlay(关键)

三层 activation 跟踪:

```typescript
type WikiActivation = {
  nodeId: string;
  level: "historical" | "session" | "turn" | "live";
  // "live" = 当前 iter 在用(corpus_search 进行中)
  // "turn" = 当前 turn 内已用(顶层激活,turn 结束降级到 session)
  // "session" = 历史 turn 已用(弱化激活)
  // "historical" = 之前 session 用过(更弱,持久,跨 session 保留)
};
```

视觉:
- live: 节点 glow + pulse 动效
- turn: 节点 highlight 边框,饱和度高
- session: 节点饱和度中等,fade
- historical: 节点轻微 tint(几乎看不出但 hover 时高亮 "之前用过")

事件订阅:
- 监听 `tool_lifecycle.start`:工具是 `corpus_search` / `corpus_read` → 该 doc id node 标 "live"
- 监听 `tool_lifecycle.completion`:同上,完成 → 该 node 从 "live" 降到 "turn"
- 监听 `assistant_done`:turn 结束 → 该 turn 的所有 "turn" 节点降级到 "session"
- 新 session 创建 → "session" 节点降到 "historical" 并保存到 sessionStorage 或 vault
  (v0 用 sessionStorage 即可,跨 session 持久化作为 future affordance)

#### C.5 性能

- 128 nodes,SVG 完全 OK,不需要 WebGL
- 边数预计 100-500(共享 tag ≥2),也 OK
- force layout 在 mount 时跑一次 simulation 收敛(~1-2s),之后 layout 固定不再 re-simulate

### D. 不做

- **不做 Corpus 全文搜索 UI**(那是 corpus_search 工具的工作)
- **不做 wiki 编辑器**(corpus 还是 git 管理,inplaceUI 编辑是 future affordance)
- **不做 sources 文件 graph**(REQUIREMENTS 明确只覆盖 wikis)
- **不做 graph 持久化布局**(每次启动重 simulate;若 UX 差再做)
- **不做 markdown link 抽取边**(v0 用 tag-based 共享边即可,markdown link parsing 是后续 enhancement)
- **不做 tag cluster 区域可视化**(v0 只显示节点 + 边,clustering visualization 后续)

### E. 单测

Backend:
- `corpus/graph.rs`:
  - 单测 fixture 4 个 wiki(2 共享 tag,2 独立)→ 验证 nodes 数 + 边权重
  - 边权重 ≥ 2 过滤逻辑
- `api/corpus.rs`:GET /api/v1/corpus/graph 返 200 + JSON shape 检查

Frontend(若有 test 设施):
- activation state machine 单测:模拟 tool_lifecycle 序列,验证激活级别转换正确
