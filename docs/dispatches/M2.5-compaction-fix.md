## 背景

step 1 录到的两份 fixture(`crates/gateway/tests/fixtures/compaction-{single-turn-burst,multi-turn-accumulation}/`)
里 `compaction_count` 全程 = 0,即便:

- `compaction-single-turn-burst/`:1 turn × 26 iter,iter-sum input_tokens 1.9M
- `compaction-multi-turn-accumulation/`:30 turn,turn 30 的 input 数组有 59 项 (30 user + 29 assistant)

为什么不触发?v3 分析(`/tmp/leek_eval/SUMMARY-v3-compaction-analysis.md`)定位了三个 bug:

| Bug | 说明 | 位置 |
|---|---|---|
| #1 | trigger 用 `last_input_tokens`(上一 iter codex usage 报告),滞后一拍 | `crates/gateway/src/agent/mod.rs:163-213` |
| #2 | `estimate_context_tokens` 在 iter 1 之后永远休眠(`if last_input_tokens > 0 { last } else { estimate }`),注释自承 fallback only | `crates/gateway/src/agent/compaction.rs:329-335` |
| #3 | `last_input_tokens` 包含 codex 服务端 builtin web_search in-call 浏览体积(leek 看不见也管不了),这部分污染信号 | 架构问题(codex builtin 服务端状态) |

**修法核心**:trigger 信号从 `last_input_tokens`(被污染)切到 `estimate_context_tokens`(只反映 leek 自己塞的 — 纯净信号)。

## Scope

### A. F1:切换 trigger 信号(`mod.rs`)

当前(`crates/gateway/src/agent/mod.rs:163-213` 附近):

```rust
if compact_trigger > 0 {
    let ctx_tokens = if last_input_tokens > 0 {
        last_input_tokens
    } else {
        compaction::estimate_context_tokens(
            &system, compaction_summary.as_deref(),
            &chat_messages, &additional_inputs)
    };
    if ctx_tokens >= compact_trigger { /* compact... */ }
}
```

改为:

```rust
if compact_trigger > 0 {
    let ctx_tokens = compaction::estimate_context_tokens(
        &system, compaction_summary.as_deref(),
        &chat_messages, &additional_inputs,
    );
    if ctx_tokens >= compact_trigger { /* compact... */ }
}
```

**保留** `last_input_tokens` 字段 —— 它仍要给 `turn_metrics_recorded.input_tokens` 累加用
(`mod.rs:337` `input_tokens += u.input_tokens as u64;`)。这是给用户看的"花了多少钱"指标,
跟 trigger 信号是不同关注点。**只在触发判断里不再用它**。

### B. F2:改进 estimator 准度(`compaction.rs`)

当前实现(`compaction.rs:329-335`):

```rust
fn estimate_tokens(s: &str) -> u32 {
    (s.len() / 3).try_into().unwrap_or(u32::MAX)
}
```

`len()/3` 是 UTF-8 字节比例,注释自承 "rough, fallback only"。F1 落地后它变成 primary signal,
准度需要改进。

**研究任务**:executor 调研以下三个选项,**用 step 1 fixture 做 calibration**(每个 iter 的
input 数组在每种 estimator 下算出来的 token 数 vs codex `usage.input_tokens` 比对),选一个。

**选项 X(推荐)**:引入 `tiktoken-rs` crate

- Pros:跟 OpenAI / codex 的 BPE tokenizer 对齐,精确
- Cons:增加依赖(~5-10 MB),codex 模型实际 tokenizer 可能跟 OpenAI o200k_base 略有差异
- 评估方法:跑 `tiktoken-rs` 对 fixture 的所有 input 数组算 token,跟 codex 报告值比;
  在 codex builtin search 不严重的 turn(单 turn iter ≤ 3、tool_call ≤ 2)误差应 < 5%

**选项 Y(回退)**:改进字符比例算法,分 ASCII / 中文 / 代码计数

- 当前 `len()/3` 对中英混合 OK,对纯英文偏低估,对纯中文偏高估
- 改进:`ascii_chars/4 + non_ascii_chars/2 + code_block_chars/3`(或类似)
- Pros:无依赖
- Cons:仍是 heuristic,误差可能 ±15-20%

**选项 Z(折中)**:保留 `len()/3` 但加 safety margin(× 1.2 - 1.5),让 estimator 偏保守

- Pros:最小改动,保留现有行为只加 buffer
- Cons:仍粗糙,只是把误差方向控制到"偏高估"(更安全)

**判断准则**:
- 偏差 < 15%(在 codex builtin search 不污染的 case 比对)
- 偏保守(偏高估 vs 偏低估,优先选高估 —— 误触发胜过漏触发)
- 依赖代价可接受(选 X 时讨论 binary size 影响)

executor 调研后**给方案 + fixture 实测数据 + 取舍理由**,PM 确认后实施。

### C. Replay regression test

新增 `crates/gateway/tests/compaction_replay.rs`(或在现有 test 文件加 module):

**测试用例至少 2 个**:

1. `replay_single_turn_burst_triggers_within_turn`
   - 加载 `compaction-single-turn-burst/` fixture
   - 缩 `LEEK_CONTEXT_WINDOW` 到某个值(executor 看 fixture 数据调,目标:让 turn 内 additional_inputs
     累积到 iter ~15 时跨阈值)
   - 模拟 leek 主循环:逐 iter 重建 chat_messages + additional_inputs,在每 iter 前用修过的
     trigger 判断,触发时跑 mock summarize(返回固定 placeholder,不调真 codex)
   - 断言:某 iter 触发 + 折叠后 additional_inputs 缩到 < threshold/2 + summary 非空 + 后续 iter
     还能继续(状态正确)

2. `replay_multi_turn_accumulation_triggers_at_turn_n`
   - 加载 `compaction-multi-turn-accumulation/` fixture
   - 缩 `LEEK_CONTEXT_WINDOW` 让 chat_messages 累积到 turn ~15-20 时跨阈值
   - 同样模拟主循环 + 断言

**Mock summarize**:为避免测试调真 codex API($$$$),需要小重构让 `compaction::summarize` 在测试
中可替换。可能做法:
- 选项 a:把 summarize 改成 trait,生产用 `CodexSummarizer`,测试用 `MockSummarizer`(返回固定字符串)
- 选项 b:在 compaction.rs 加 `#[cfg(test)]` 路径用 env var 或全局函数指针注入 mock
- 选项 c:直接把 compact 函数拆开,把 summarize 调用提到外面,让 test 自己控制

executor 选简洁的一种。**不要让测试调真 codex**。

**关于 fixture 数据的细节**:
- fixture 的 `events.json` 含每个 turn 的 `message_created` 事件 —— 用这些重建 chat_messages
- fixture 的 `transcripts/turn-N-iter-M-request.json` 含每 iter 的完整 input 数组 —— 用来重建
  additional_inputs(只取 leek 自己工具的 function_call/output 对,过滤掉 codex builtin items)
- fixture 的 `metadata.json` 含每 turn 的 input_tokens / output_tokens / cost_usd —— 可参考但不依赖
