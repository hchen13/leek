# M2.5 step 1:录 compaction 的真实长 session regression fixture

> **Dispatch spec(2026-05-21,v2)。** M1.8 合入了 auto-compaction,但 T1-T9 所有 e2e 测试中
> `compaction_count = 0` —— 这段代码合入以来从未在 e2e 路径上真正跑过。M2.5 的目标是
> 把 compaction 修对,但要"修对"先得有验证手段。这个 dispatch 只做 step 1:**录一份
> 真实长 session 作为永久 regression fixture**。step 2 (修 estimator + 切 trigger 信号
> + 加 replay test) 和 step 3 (cost cap) 分别 dispatch,不在本次范围内。
>
> **v1 → v2 修订记**(2026-05-21,在 worker 第一次 attempt 后):
> - v1 用 `INPUT_TOKEN_STOP=200,000` 做终止条件,误把 `turn_metrics_recorded.input_tokens`
>   当 context window 占用比。实际它是 turn 内 iter sum(`crates/gateway/src/agent/mod.rs:337`
>   `input_tokens += u.input_tokens as u64;`)。结果第 1 个 turn 跑了 26 iter,iter sum
>   就 trip 了阈值,只录到 1 turn 的"单 turn iter 爆炸"形态。
> - v2:**双形态 fixture** —— v1 录到的 1-turn-burst 保留作辅助样本(改名为
>   `compaction-single-turn-burst/`),v2 再录一份 multi-turn (`compaction-multi-turn-accumulation/`)
>   作为主菜。step 2 的 replay test 会分别 replay 两种形态。
> - v2 stop 条件:`MAX_TURNS=30` + `COST_CAP_USD=200` + codex `context_too_large`。
>   **去掉** `INPUT_TOKEN_STOP`。
> - v2 prompt 序列适度调淡(让 leek 单 turn 不爆 25+ iter),让"多 turn 累积"形态成立。

## 背景

- compaction 当前用 `last_input_tokens`(codex 报告的 `usage.input_tokens`)做触发判断
- 该信号被 codex 内部 builtin web_search 的 in-call browsing 污染 —— 同一份 `last_input_tokens`
  里 leek 真正塞的部分(可 compact)和 codex 服务端翻书的部分(不可 compact)混在一起
- step 2 要把这个信号换成 leek-side estimator,但要先有真实长 session 作 ground truth
- v1 已录了"单 turn 26 iter"密集型 fixture,**那份不浪费、留作辅助样本**。v2 加录一份"多 turn 累积"型 fixture 作为 step 2 的主测对象

### 4. 导出 fixture

目标路径:`crates/gateway/tests/fixtures/compaction-multi-turn-accumulation/`

结构(与 v1 一致):

```
compaction-multi-turn-accumulation/
├── README.md          # 用途 / 何时重录 / 怎么重录 / 当前快照 + 形态归类
├── metadata.json      # 每 turn 关键指标(给 replay test 用)
├── session.json       # session 元信息(model, system prompt 等)
├── events.json        # 全部 events 序列(原样 export)
└── transcripts/
    ├── turn-1-iter-1-request.json
    ├── turn-1-iter-1-response.txt
    └── ...
```

`metadata.json` 必含字段(与 v1 schema 完全一致):

```json
{
  "recorded_at": "2026-05-21T...",
  "leek_git_rev": "...",
  "codex_model": "...",
  "corpus_git_rev": "...",
  "session_id": "...",
  "total_cost_usd": 0,
  "total_wall_clock_ms": 0,
  "stopped_by": "max_turns|cost_cap|context_too_large|other",
  "turns": [
    {
      "turn_id": "...",
      "turn_index": 1,
      "user_message_preview": "前 200 字...",
      "input_tokens": 0,
      "output_tokens": 0,
      "tool_call_count": 0,
      "iteration_count": 0,
      "wall_clock_ms": 0,
      "cost_usd": 0,
      "compaction_count": 0
    }
  ]
}
```

`README.md` 必须说清:
- fixture 是给谁用的(M2.5 step 2 的 compaction replay regression test)
- **形态归类**:multi-turn × N turn × 平均 M iter/turn,chat_messages 跨 turn 累积型
- 与 single-turn-burst 的对比(两份覆盖 compaction 两种触发场景)
- 何时需要重录:corpus 大改 / codex 模型升级 / tokenizer 切换 / system prompt 重写
- 怎么重录:指向 `scripts/record-compaction-fixture.sh`,给出环境变量表
- 当前数据反映的 leek 版本(git rev)、corpus 版本、codex model、recorded_at

### 7. 异常处理

| 情况 | 怎么办 |
|---|---|
| 录制中 compaction 触发了 | 记到 metadata,继续跑。**这反而是好事** —— 说明我们录到了真实触发数据 |
| codex 返回 context_too_large | 停止,把已录到的部分存下来,`stopped_by: context_too_large`,这是宝贵的边界 fixture |
| 某 turn 超时 > 5 分钟 | 跳过该 turn,metadata 里标 `wall_clock_ms` 为实际等待时间,标记 `timeout: true`,继续下一 turn |
| codex 5xx | 重试一次,还失败就停止录制并 report |
| cost 累计超过 `COST_CAP_USD` | 停止录制并 report,不要继续烧 |
| spec 跟现实又不对得上 | **stop 来问 PM**,不要 ad-hoc 改 spec —— 这次 v1 那种"按 spec 字面跑完停手等 PM"的判断方式是对的 |

## 执行建议(meta)

- **不用 subagent** —— 长程但窄面任务,用 subagent 反而碎片化
- **关键监控点**:每 turn 后立刻 print 当前 turn_index / accumulated_cost / max_iter_in_turn,
  够清楚自己跑到哪了
- **录制全程不要中断 leek backend**(同一个 session 跨进程不可恢复)
- **prompt 调淡的兜底**:如果发现某 turn 已经爆 15+ iter,改下一个 prompt 让它更窄(加
  "只用 corpus 不要 web_search" / "200 字以内 done")
- **数据 sensitivity**:巴菲特投资学习无敏感信息,fixture 进 git 安全。但**别 commit codex
  auth token** 或任何环境变量泄漏到脚本里
