## 4 P0 任务

### P0-1: `llm_transcripts` UNIQUE constraint 改 INSERT OR REPLACE

**症状**:retry 同 iter 时,codex client 试图插第二条 `llm_transcripts` 行,UNIQUE(turn_id, iteration) 失败,日志一片 WARN(stress 实测 26 个实例)。Archive 实际丢失了。

**修法**:
- 找到 codex.rs 内 `llm_transcripts` insert 语句
- 改 `INSERT INTO ... VALUES (...)` → `INSERT OR REPLACE INTO ... VALUES (...)`(SQLite 语法)
- Retry 时直接覆盖前次 archive,debug 视角能看到"最新一次"调用的真实 request/response

**单测**:测试 retry 1+1 后,llm_transcripts 表里同 turn+iter 只有 1 行,且内容是 retry 后的。

### P0-2: codex stream `agent_thinking` heartbeat event

**症状**:codex 在深 reasoning(model thinking)阶段不 emit token,gateway 也不 emit user-visible 事件,前端看就是死寂。stress B2 case:1 个 research_sentiment 调用后,codex 思考 14 分钟没任何输出 → user 视角 = 死机。

**修法**(loop_core.rs):
- 在 codex stream 消费循环里加一个 `tokio::time::interval(60s)` 旁路
- 每 60s 若 stream 没新事件,emit `agent_thinking` event:`{turn_id, iteration, elapsed_silent_s, last_activity_kind}`
- M3.3 substantive-only idle_timeout 不变(180s 真死寂照样杀);此 event 只是 user heartbeat,不影响杀线程
- 前端 TurnStatusPill(已有 M3.2 描述)可消费这个 event 显示"思考中 N 秒",但这部分前端改 follow-up,不在本 dispatch scope

**单测**:mock codex stream 90s 无 token,assert 1 个 agent_thinking event 在第 60s emit。

### P0-3: subagent default 硬 iter cap

**症状**:stress C1 comparison subagent 嵌套 quick-screen 跑到 iter 13(失控),主 agent 88 tool calls,25min 仍 not finished。`max_iterations` 是 opt-in(M3 设计),实际 user 都不设,subagent 失控时无硬刹。

**修法**:
- `AgentDef` (`crates/gateway/src/agents/agent_def.rs`) 加 `pub default_max_iterations: Option<u32>` 字段
- 5 个内置 AGENT.md frontmatter 加 `default_max_iterations`:
  - `quick-screen`: 8(应该 < 2 分钟完事,8 轮够)
  - `comparison`: 20(并行 task delegate,5 子 ×  3 iter + 1 汇总 ≈ 20)
  - `deep-review`: 30(深度复盘,合理上限)
  - `corpus-expert`: 12(几次 corpus_search + 一次回答)
  - `general-purpose`: 25(default)
- `agents/loader.rs` 解析这个 frontmatter
- `agent/subagent.rs::apply_agent_overrides` 把 `guards.max_iterations` 设成 default(若 user 没显式设)
- 主 agent default 也加:50(主 agent 默认 50 iter,够 deep + 多 subagent)

stop_reason 用现有 `iteration_cap_exceeded`(M2.6 已有)。

**单测**:loader 解析 frontmatter + apply_agent_overrides 设了 cap + 50 iter exhausted 触发 cap_exceeded 事件。

### P0-4: `cost_cap_usd` default 不再 null

**症状**:M3.6 把 cost_cap default 设 null(user opt-in),实测 user 永远不 patch,subagent C1 跑 1500s 没硬停。Spec 是 fault-tolerant 但实际是 fault-amplifying。

**修法**:
- `crates/gateway/src/config.rs::Config::default()` `cost_cap_usd` 默认改成 `Some(5.0)`(主 agent 单 turn 上限 $5)
- 5 个内置 AGENT.md 加 `cost_cap_usd` frontmatter:
  - `quick-screen`: 0.3(轻量)
  - `comparison`: 5.0(并行多 subagent + 汇总)
  - `deep-review`: 8.0(深度复盘允许多)
  - `corpus-expert`: 0.5(纯 corpus 查询便宜)
  - `general-purpose`: 5.0(default)
- `agent/subagent.rs::apply_agent_overrides` 把 `guards.cost_cap_usd` 从 AgentDef 拉
- M4.1.1 测试可能有 default null 假设,跟着更新

**单测**:default Config 有 5.0;agent override 5 个内置都有合理值;cost cap 触发产 `cost_cap_exceeded` 事件 + assistant message 显式说明(已有,不动)。
