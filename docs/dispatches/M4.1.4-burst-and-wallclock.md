## 3 任务

### Task 1: codex 并发 semaphore(P1)

**症状**:5 lane 同发 5 个 turn → 5 个 codex POST 同时打 backend → 某 1-2 个被 rate-limit → 退避 30s/60s/2min/5min 直到通过。用户看就是 5 分钟死寂。

**修法**:
- gateway state 加一个 `tokio::sync::Semaphore` 限 codex 并发(初 cap=3,作为 GuardConfig.codex_max_concurrent,可改)
- codex.rs::call(...) 进入前 `acquire()`,出去后 release
- 等待 semaphore 时 emit `agent_queued` 事件(lifecycle surface,payload `{turn_id, iteration, queued_at, queue_position}`)— 让用户看"排队中 N 位"
- queue_position 可以是个 hash(`semaphore.available_permits()` reverse)
- AppState 加 `pub codex_sem: Arc<Semaphore>` 字段,init 用 `Semaphore::new(3)`
- 单测:mock 4 个并发 codex 调用,验证只 3 个同时跑,第 4 个等;agent_queued 事件触发

### Task 2: heartbeat 扩展到 HTTP retry backoff

**症状**:M4.1.3 heartbeat 0 个实测触发。codex stream 接通后 ~30s 一 Ping 保持 deadline 重置;**真正用户看到死寂的 HTTP retry 阶段**(stream 还没接通)heartbeat 不在那 layer。

**修法**:
- codex.rs::call(...) 内,在每次重试 sleep 之间(M3.4 `provider_retry_attempt` event 之后) 加一个 30s heartbeat tick
- 每 30s emit `agent_retrying_upstream` 事件 `{turn_id, iteration, attempt, backoff_remaining_s, retry_kind}`
- Sleep 用 `tokio::time::sleep` 中断式(`tokio::select!` + interval),不要直接 `sleep(backoff)`
- 注意:M3.4 的 `provider_retry_attempt` 是每次 *attempt 之前* 一发;新 `agent_retrying_upstream` 是 *backoff 期间* 每 30s 一发
- 前端 TurnStatusPill 后续可消费,本 dispatch 不动前端

### Task 3: wall_clock_secs 硬终止(取代 soft prompt)

**症状**:M3 / M4.1.3 的 wall_clock_secs default=1800s 只是 soft prompt 提示(剩 10/5/2/1min 时给 model 提示),**不是硬 kill**。C2 跑 25min+ 还没停。

**修法**:
- guards.rs:`wall_clock_secs` 仍然 default 1800s
- loop_core.rs:loop start 记录 `turn_started_at`,每 iter 开头 check `now - turn_started_at > wall_clock_secs` → 强制 break + stop_reason = "wall_clock_exceeded"(M2.6 stop_reason 字符串已有)
- soft prompt 注入逻辑保留(M3 时间到剩 10/5/2/1 min 时给 model hint,让 agent 自己合理收尾);硬 cap 是兜底
- subagent 也用同 cap(M3.6 subagent inherit guards),但因 subagent 是 nested inside parent turn,subagent 的 wall_clock 应从 *subagent 自己的 started_at* 算,不要从 parent 算
- 单测:mock turn 跑到 1801s,强制 break + stop_reason 正确
