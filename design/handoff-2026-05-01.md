## 2. 已经达成的设计共识

**形态层面：**
- **不是一个 agent，是一个投研操作系统**（agent core + corpus 双核 + 多 frontend）
- **多 frontend 都要做，但分阶段**——P1 web + CLI + MCP HTTP；P2 TUI + Claude Code skill 包；P3 Bloomberg-style 桌面 dock app；P4 messaging
- **Web 起步，桌面 app 后做**（用户拍板）
- **chat-canvas 形态**——chat 主轴 + panels 动态生成（chatgpt + warp 合体）
- **proactive 浏览模式 + reactive 指令模式 共存**

**架构层面：**
- **gateway 模式**（参考 hermes-agent）——长跑 daemon + 多个 adapter（CLI / TUI / Web / MCP / skill / ACP）作为门，没一个 adapter 拥有 lifecycle
- **MCP 的两种 transport** 必须区分清楚：stdio（父进程子进程）vs HTTP/SSE（独立长跑）。我们要的是后者。
- **agentic UI = CLI + skill + MCP 三种入口的组合**，用户根据自己习惯选哪个一等公民
- **multi-user 从 day-1 设计**（即使 MVP 单用户）——gateway 启动接受 user-id；corpus 永远 read-mostly；agent 写入只能进 inbox/

**数据/知识分层：**
- **corpus 保持 universal**（可公开、可共享、对任何用户都成立的静态智慧），物理上仍住在 `finance-giant/corpus/`
- **decisions / holdings / reviews / mandates 不进 corpus**——它们是 user-specific runtime state，去单独的 *user vault*
- solo / open-source 模式：vault = `~/.leek/vault/`（默认假设，§5 仍开放讨论是否走 XDG），用户自管
- cloud / 多用户模式：vault per-user，corpus 由官方统一维护
- agent tool 层有两套 resolver：`corpus://...` 和 `vault://...`，可以跨链

**反馈环：**
- **promotion pipeline 是 corpus 的入口控制**——hermes 风格的 background loop 在 session / phase 结束后复盘，输出"哪些值得进 corpus"的候选
- solo：候选写入 `corpus/inbox/`，用户在 Obsidian 直接审核 → 手动 promote
- cloud：候选进入 *统一 curation queue*，admin 审核 → 合并
- corpus 永远 read-mostly，agent 写入只能进 inbox

**投资动作：**
- agent 必须输出 *investment actions*（仓位 / 止损 / 期限 / 复盘 schedule），不止"研究意见"
- mandate 默认 = 普通股民（长期权益、不碰复杂衍生品默认关、单标位置上限、最大回撤容忍）；用户可改

**self-improving loop（"越来越接近真相"）：**
- 每个决策 → 复盘 → corpus 升级
- corpus 增长率 = 系统改善率
- 这是三个商用 reference 都没有、用户 unique 的护城河

你的反馈让我意识到我说"MCP server"时偷换了概念——你想的那种生命周期是 MCP 的 *一种*，不是全部。让我先把这层澄清，再统一回应你 5 点反馈。

## MCP 的两种 transport 决定了两种生命周期

- **stdio transport**（你脑子里那种）：父 agent（Claude Code / openclaw）启动时 spawn 子进程，关了就死，状态随父走。
- **HTTP / SSE / streamable-http transport**：独立长跑 server，多 client 远程接入，关任何 client 不影响 server 自身的 cron / scheduler / state。

我之前说"day-1 必须 MCP server"——指的是后者，*长跑 daemon + HTTP transport*。但单说"MCP server"误导了你。

## 这正好就是 hermes-agent 的 gateway 模式

我刚扫了 `~/research/repos/hermes-agent/` 的目录结构（没读源码细节），它已经长成你脑子里那个东西：

```
hermes-agent/
  gateway/                    # 核心：长跑 daemon
  agent/                      # agent 引擎
  cli.py + hermes_cli/        # CLI 入口
  tui_gateway/ + ui-tui/      # TUI 入口
  web/ + ../hermes-webui      # Web 入口
  mcp_serve.py                # MCP 入口（其中一种）
  acp_adapter/                # ACP 入口
  cron/                       # 定时任务
  skills/ + optional-skills/  # skills
  plugins/                    # 插件
```

**核心洞察：gateway 是长跑的 daemon，CLI / TUI / Web / MCP / ACP / Skill 都是 *adapter*——通往 gateway 的门，没一个拥有 lifecycle。** 关 Claude Code / 关 web tab 都不影响 gateway 本体；gateway 的生死由 `start/stop` 命令或 system service 管。

这正回答你反馈 1——**agentic UI = CLI + skill + MCP，三种都是 gateway 入口，用户自选哪个一等公民**：
- 喜欢 shell → CLI 一等公民（`leek "AAPL 怎么样"`）
- 主用 Claude Code → skill 包塞进 `~/.claude/skills/` 是一等公民，MCP HTTP 当工具是二等公民
- 用其他不支持 skill 的 agent → MCP HTTP 一等公民

三种入口背后是 *同一个 gateway*。

## 你 5 点反馈如何落到架构里

**反馈 2 + 4：corpus / vault 分层**——day-1 就分。corpus 保持现在双层 sources/wikis 静态智慧，路径不变；vault 是新建的 per-user runtime store，*目录结构看起来像 corpus*（同样用 frontmatter + wikilink）但物理上分离：
- solo / 开源：vault = `~/.leek/vault/`，用户自管自维护
- cloud 多用户：vault = per-user 存储（DB / S3 prefix），corpus 由官方统一维护

agent tool 层有两套 resolver：`corpus://...` 和 `vault://...`。两个 namespace 之间能跨链——decision artifact 可以引用 corpus 的概念页，复盘可以反向 link 回 corpus。

**反馈 5：自学习 loop = promotion pipeline**——hermes 风格 background loop，每轮有效对话 / 每个任务阶段结束后触发：
- 复盘本轮看到的研报、行情、新闻、分析
- 输出 *候选*：哪些值得进 corpus
- solo：候选写 `corpus/inbox/`（用户在 Obsidian 直接 review → 手动 promote）
- cloud：候选进 *统一 curation queue*，admin 审核 → 合并

**这个 pipeline 是 corpus 完整性的最后一道闸门**——agent 能写 inbox 是协议化的，但 inbox → 正式 corpus 永远要人审。

**反馈 3：multi-user from day-1 的物理痕迹**——MVP 单用户也必须做这两条，否则未来切 cloud 要重写：
1. gateway 启动接受 *user-id*（默认 OS 用户名），所有 vault 路径打 user-id 前缀
2. corpus 永远 read-mostly，agent 写入只能进 `inbox/`，不能直接编辑 `wikis/` / `sources/`——这条规则就是 cloud admin curation 的 day-1 雏形

两条都不增加 MVP 复杂度，但保住未来路。

三个共用同一个 gateway 后端。
